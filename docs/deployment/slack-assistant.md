# Shared Slack assistant

The integration is disabled by default. It uses the existing `StockflowAssistant`, durable turn runner, native approval previews, action audits and safe retry service. One configured **administrator** owns and executes every linked conversation. Slack user IDs identify the actual authors and decision makers in `assistant_slack_inputs` and `assistant_decision_claims`, independently of `actor_user_id` in the domain audit. Match audit `conversation_id` + `tool_call_id` to the decision claim; `turn_id` identifies the admitted input.

## Configuration and rollout

1. Migrate the application and configure `AI_ASSISTANT_ENABLED`, the existing provider and assistant queue. Keep `SLACK_ASSISTANT_ENABLED=false` during setup.
2. Set `SLACK_ASSISTANT_ADMIN_USER_ID` to the intended existing administrator, `SLACK_ASSISTANT_WORKSPACE_ID` to the Slack team ID, `SLACK_ASSISTANT_BOT_USER_ID` to the bot user ID, `SLACK_SIGNING_SECRET` to the app signing secret, and the existing `SLACK_BOT_USER_OAUTH_TOKEN` to its bot token. Never put these values in tracked files. The notification token configuration has not moved.
3. Extend the existing Slack app with bot scopes `app_mentions:read`, `channels:read`, `channels:history`, `groups:read`, `groups:history`, `users:read`, `chat:write`. Reinstall the app after changing scopes. Enable bot events `app_mention`, `message.channels` and `message.groups`. No DM subscriptions are needed. Invite the bot to each channel it should access. Private channel access requires membership. Verify actual token access to `conversations.replies`; a successful notification alone does not prove history access.
4. Configure Events Request URL `https://YOUR_HOST/slack/events` and Interactivity Request URL `https://YOUR_HOST/slack/interactivity`. Both verify the raw-body HMAC and a five-minute timestamp window before parsing; event/interaction callbacks must match the configured workspace. URL verification challenges are signed as well. Only these two paths are exempt from browser CSRF protection.
5. Enable `SLACK_ASSISTANT_ENABLED=true` once configured, rebuild Laravel configuration/routes and restart workers. Run `php artisan stockflow:assistant:diagnose` and `php artisan stockflow:slack-assistant:diagnose --live --channel=C_STORE --channel=C_GENERAL`. The latter performs **read-only** identity, membership and paginated history checks; it never posts a test message. It requires an existing message in each test channel. Check the public endpoint subscription verification and interactivity in the Slack app dashboard separately.
6. Run the existing `assistant` connection / `assistant` queue workers and the Laravel scheduler. Example: `php artisan queue:work assistant --queue=assistant --timeout=180 --tries=1`. Keep the queue retry-after greater than the worker timeout, and use the shared Redis lock store on all instances. The minute maintenance job recovers persisted ingress/outbox records and waiting turns when queue dispatch or workers fail. Native turn maintenance still marks abandoned running work failed and preserves uncertain external outcomes.
7. Only after those checks, perform the authorized controlled live test in **one store channel and one general channel**. Mention the bot first; continue as a second human without mentioning it; view and reply in Stockflow; select a store in the general thread; propose a reversible mutation and approve from the other interface; repeat a stale button; test cancellation. Observe the saved domain result, author/approver records and delivery journals. Do not treat HTTP 200 alone as proof of an executed assistant turn.

This checkout has no configured live Slack credentials or verified reachable deployment. No real Slack message has been sent and the controlled live tests remain a deployment dependency.

## Behavior

- First activation requires `<@BOT_USER_ID>`. All later human messages in that channel thread are admitted; bot messages, edits, deletes and DMs do not trigger actions. One shared conversation is created per workspace/channel/root timestamp. Duplicate `message`/`app_mention` deliveries share a durable key.
- The initial store is resolved from the existing store Slack configuration using the exact stable channel ID or the exact current Slack channel name returned for that ID. No name similarity is used. A unique matching store is snapshotted; no match means company-wide context, multiple matches require clarification. Configuration changes never replace the saved conversation store. Prefer stable IDs in store settings to survive Slack channel renames.
- Previous accessible thread messages are imported once, atomically after complete pagination, marked as historical reference only. Encrypted page checkpoints preserve the next cursor across rate limits and worker restarts. The activation and later inputs are the only executable requests. Failure to read complete history prevents generation and exposes Retry in Slack and the app.
- Linked web inputs and Slack inputs use the same short admission transaction and distributed execution lock. Messages remain queued while awaiting a decision. Individual button decisions are claimed once, then gathered into the complete batch required by the native SDK. Batch execution takes priority over queued text; stale decisions cannot start a second mutation.
- The shared active store is changed through the existing approved store-switch operation. Browser store selection does not overwrite linked context. The application displays the Slack link, active store and sharing notice, and polls the linked conversation for messages from other participants.
- Web messages are posted as `Stockflow · administrator-email`; assistant replies are bot-authored and labeled as Stockflow. Slack-authored user inputs include their real Slack user ID in the app. Buttons support approvals, rejections, choices, cancellation of queued/running work and existing safe failed-turn retry. The existing rule blocking retries of uncertain external effects still applies.
- Outgoing text is split into bounded Slack sections, with the existing structured approval summary and choice buttons. Delivery is independent of provider/domain execution. After an interrupted delivery, the retry searches paginated thread history for the saved delivery metadata before posting again. HTTP 429 preserves Retry-After. If reconciliation history is inaccessible, delivery stays failed instead of blindly repeating the post.
- App deletion detaches the thread and removes its app conversation. Existing Slack posts remain, and delivery workers stop posting for the detached conversation. A later fresh mention can start a new app conversation. Historical pre-activation requests remain historical in that new conversation.

## Operations and evidence

`stockflow:slack-assistant:diagnose` prints pending and failed ingress/outbox counts without payloads or secrets. `assistant_slack_events.error`, `available_at` and `attempts` expose intake/history failures; `assistant_turns` and `assistant_turn_events` expose execution; `assistant_slack_outbox.error`, `message_ts` and `sent_at` expose delivery independently. Exceptions are also reported through Laravel's existing error reporting. Incoming payloads and outgoing payloads are encrypted at rest with the application key.

Repeated outbound failures do not retry domain actions. Investigate missing scopes, channel membership, workspace/bot identity, rate limits, provider configuration, scheduler health and queue heartbeat before retrying. Keep the application encryption key available during queue and journal retention. Existing notification and assistant regression tests remain applicable.

Protocol references: [signed requests](https://docs.slack.dev/authentication/verifying-requests-from-slack/), [thread history and pagination](https://docs.slack.dev/reference/methods/conversations.replies/), [message events and subtypes](https://docs.slack.dev/reference/events/message/).
